## Schema Conflicts

### Critical Name Collision: `Collection` model

**Upstream `Collection` (simple bookmarks table):**
```
model Collection {
  userId    String
  promptId  String
  createdAt DateTime
  @@id([userId, promptId])
  @@map("collections")
}
```

**Phase 1 spec `Collection` (full collections-as-entities):**
```
model Collection {
  id          String @id @default(cuid())
  slug        String
  name        String
  description String?
  visibility  CollectionVisibility
  ownerId     String
  items       CollectionItem[]
  members     CollectionMember[]
  @@unique([ownerId, slug])
  @@map("collections")
}
```

**This is a direct, destructive name collision.** Both map to the `collections` table. Upstream has already shipped this model, with a migration at `20260104210000_add_collections`, and the fork already has it too (they are in sync on this migration). The Phase 1 spec proposes **replacing** the existing flat `collections` table with an entirely different schema: named, visibility-controlled, multi-item collections. This requires dropping the current `collections` table and re-creating it with a different structure.

The fork's current `Collection` model (which matches upstream) is used in:
- `src/app/collection/page.tsx`
- `src/app/api/collection/route.ts`
- `src/components/prompts/add-to-collection-button.tsx`

All of these will break when the table is replaced.
